## 9. 실사용 조건 실측 (2026-08-23, TestFlight 빌드 / 운영 번들)

프로브가 아니라 **실제 구현**(`kr.co.anbucheck.live.HeartbeatNSE`)을 TestFlight로 설치하고
서버 트리거로 검증한 기록.

### 9.1 ★ 엔드투엔드 성공 — 앱이 죽은 채, 탭 없이 전달됐다

세 지점이 독립적으로 일치했다:

```
기기   06:49:53  HeartbeatNSE(Foundation)  [HeartbeatNSE] nse sent
기기   06:49:59  Data Usage HeartbeatNSE — WiFi in/out: 8993/2394
기기   06:50:01  wrote .../AppGroup/.../group.kr.co.anbucheck.live.plist
서버   06:49:53  POST /api/v1/heartbeat 200 OK
서버   06:49:53  NORMAL 발송 완료 → 보호자 폰에 알림 도착(사용자 확인)
```

### 9.2 잠금·화면 꺼짐은 원인이 아니다 (1.8초 만에 실행)

| 발사 | 확장 실행 | 지연 |
|---|---|---|
| 07:01:44 | 07:01:45.8 | 1.8초 |
| 07:11:13 | 07:11:14.8 | 1.8초 |
| 07:12:14 | 07:12:15.9 | 1.9초 |

전부 **잠금 + 화면 꺼짐 2분 이상** 상태. "폰이 자면 푸시를 못 받는다"는 가설은 기각됐다.

### 9.3 ⚠️ 정각 1회 발사는 유실될 수 있다 — APNs 보관 덮어쓰기

06:00 정시 트리거는 **기기에 도달하지 않았다**:

- 성공 문구도 원본 문구도 **둘 다 없었다** (확장이 실패했다면 원본이 떴어야 한다)
- `HeartbeatNSE` 크래시 리포트 **없음**
- 06:15 오프라인 폴백이 **발화**(확장이 제거 경로에 도달 못 함)
- 보호자 폰에 그 시각 알림 **없음** → 서버에 heartbeat가 도달조차 안 함

그런데 **29초 뒤 같은 토큰**으로 보낸 보호자 알림(06:00:39)은 06:01에 정상 표시됐다.
APNs는 기기가 도달 불가일 때 **토큰당 최신 알림 하나만 보관**하므로, 뒤에 온 알림이
보관돼 있던 트리거 푸시를 덮어쓴 것으로 보인다. 밤새 깊은 유휴 + 같은 시각에 겹친
안드로이드 대상자 heartbeat가 조건을 만들었다.

→ **대응: 정각 / +5분 / +10분 재시도**(`job_ios_heartbeat_trigger`).
   첫 성공 시 `last_seen` 갱신으로 자동 중단되고, `apns-collapse-id` 덕에 사용자에게
   보이는 알림은 하나로 대체된다. **연속 2회 발사가 확장을 각각 실행시킴을 실측 확인**
   (9.2) — collapse-id가 후속 전달을 억제하지 않는다.

### 9.4 ⚠️ 발화한 폴백 알림은 pending 제거로 지워지지 않는다

`removePendingNotificationRequests`는 **예약된** 요청만 지운다. 폴백이 이미 발화한 뒤
늦게 안부가 전달되면(재시도 성공·통신 복구) "누르지 않으면 오늘의 안부가 전달되지
않습니다"가 트레이에 남아 **이미 전달된 안부를 두고 거짓 안내**를 한다.
실측: 06:15 발화 → 06:49 전송 성공 → 알림 잔존.
→ `removeDeliveredNotifications`를 함께 호출한다(그날치 식별자 하나뿐이라
§2.5.2 "예약은 건드리지 말 것" 불변 규칙과 충돌하지 않는다).

### 9.5 ⚠️ 진단 도구는 운영 사용자에게 닿을 수 있는 형태로 두지 말 것

즉시 발사 엔드포인트를 만들 때 대상 조건(`supports_push_heartbeat`, `invite_code`)을
빠뜨려 **모든 iOS 기기**가 대상이 됐고, 확장이 없는 **실사용자 22명**에게 일요일 아침
06:40에 "안부 확인이 필요합니다" 알림이 1회 발송됐다(부수효과는 없음 — 구버전엔 확장이
없어 전송·상태 변경이 일어나지 않는다). 진단 쿼리에도 **정규 잡과 동일한 대상 조건을
못박을 것**.

### 9.6 진단 절차 (반복 주기를 하루 → 1분으로)

정규 잡은 "예약시각 정각 + 오늘 미수신"에서만 발화하고, 앱을 열면 2차 안전망이 그날치를
소모해 조건이 깨진다. 그래서 즉시 발사 엔드포인트가 필요하다.

```bash
cd anbucheck-server
curl -s -X POST "$BASE/api/v1/admin/ios-heartbeat-trigger?collapse=true" \
  -H "X-Admin-Key: $(grep '^ADMIN_SECRET_KEY=' .env | cut -d= -f2-)" | python3 -m json.tool
# 응답에 supports_push_heartbeat / is_gs / last_seen / schedule이 함께 나와
# "왜 안 갔는가"를 한 번에 확인할 수 있다.

idevicesyslog -u <UDID> | grep "HeartbeatNSE(Foundation)"   # ⚠️ USB 필수(무선 불가)
```

⚠️ **판독 시 주의**: 성공 알림은 `.passive` + 무음이라 **화면을 깨우지 않는다.**
"알림이 안 왔다"고 판단하기 전에 알림센터를 직접 확인할 것(실제로 한 번 오인했다).

## 10. 이틀 연속 관측 (2026-08-25 / 08-26) — 서버 트리거 실조건

예약시각 06:00, 테스트폰은 책상 위에 두고 밤새 건드리지 않음(셀룰러 없음, 핫스팟 전용).

### 10.1 ★ APNs 보관 규칙이 이 설계의 핵심 제약이다 (문서 근거)

기기가 도달 불가일 때 APNs는 **앱당 최신 알림 하나만 보관**하고, 새 알림이 오면 이전
것을 **버린다**(coalescing). 오래 오프라인이면 보관분도 폐기된다.
→ 정각 1회 발사는 (a) 기기가 그 순간 도달 불가이고 (b) 그 사이 다른 푸시가 오면
**흔적 없이 사라진다.**

### 10.2 8-25 — 망이 아예 없던 날

핫스팟이 꺼져 있었다. 서버는 06:00:03 / 06:05:05 / 06:10:06 **세 번 다 발사**했고
전부 APNs에서 멈췄다. **재시도가 실패한 게 아니라 받을 경로가 없었다** — 이 날 데이터를
재시도 정책의 근거로 쓰면 안 된다.

### 10.3 ★ 8-26 — 딥 슬립 → 물리적 이동으로 깨어난 순간 전달

```
06:00:05  서버 발사 (1회 확인)
          → 폰 딥 슬립 + 핫스팟 → APNs 보관
06:06~08  사용자가 폰을 집어 옮김 → 기기가 깨어나며 APNs 재연결 → 전달
06:09:32  heartbeat 서버 도착 → 보호자에게 알림
```

**앱을 열지도, 알림을 탭하지도 않았는데 안부가 전달됐다.** 기능은 성공이다.
다만 "정시"는 아니었다 — **+9분 32초**. 미수신 체크(+2h)보다는 훨씬 이르다.

⚠️ **여기서 얻은 교훈**: 잠금·화면 꺼짐은 전달을 막지 않는다(§9.2에서 1.8초 실측).
막는 것은 **장시간 유휴로 APNs 연결이 끊긴 상태**이고, 그 상태는 기기가 무언가로
깨어나야 풀린다. 실사용자는 폰을 자주 집으므로 자연히 풀리지만, **탁자에 놓인 채
아무도 건드리지 않는 대상자 폰**은 이 앱의 표준 시나리오다 — 그때 얼마나 걸리는지는
**아직 측정되지 않았다.**

### 10.4 ⚠️ 확장이 **옛 예약시각으로 키를 만든다** (실측 확인)

```
heartbeat_logs:  08-26 06:09:32   key = 2026-08-26_10:00
devices.heartbeat_hour/minute:    06:00   (8-24 16:26 PUT으로 변경됨)
```

App Group의 `hb_hour/hb_minute`가 갱신되지 않아 확장이 **옛 값(10:00)**으로 키를 만들었다.
당시 빌드에는 `armOfflineFallback` 직전 `SharedStore.exportToExtension()`을 호출하는
수정(커밋 `8e39497`)이 **탑재되지 않은 상태**였고, 그 결함이 그대로 드러난 것이다.

날짜는 맞으므로 걸음수 귀속·당일 판정은 정상이지만, **같은 날 앱이 `_06:00` 키로 또
보내면 서버 dedup(키 문자열 일치)이 걸리지 않아 중복 기록이 남는다.**

### 10.5 ⚠️ Railway 로그는 **배포 시작 시점부터만** 보인다 — 두 번 오판했다

로그 화면 상단의 `You reached the start of the range → <시각>`이 **그 배포가 시작된
시각**이다. 그 이전 구간은 `HISTORY`에서 **이전 배포를 열어야** 보인다.

이 함정 때문에 "재시도가 발사되지 않았다"고 두 번 판정했다가 근거가 무너졌다.
**로그를 읽기 전에 항상 range 시작 시각부터 확인할 것.**

또한 **배포는 예약시각(06:00·07:00 등) 근처를 피한다** — 재배포 시 컨테이너가 재시작되며
그 분의 스케줄러 잡이 건너뛰어질 수 있고, 관측이 오염된다.

### 10.6 미결 — 06:05 / 06:10 재시도가 실제로 발사됐는가

8-26에 확인하려 했으나 §10.5의 배포 경계 때문에 결론을 내지 못했다.
`last_seen`은 06:09:32(그날 첫 heartbeat)이고 `recent_logs`에도 그 한 건뿐이므로,
**06:05 시점에 조건(`오늘 미수신`)은 참이었다.** 그렇다면 발사됐어야 한다.
다음 관측에서 **이전 배포 로그까지 포함해** 확인할 것.

### 10.7 진단 도구를 만들다 낸 실수 두 건 (재발 방지)

1. **대상 조건 누락 → 실사용자 22명에게 발송**(§9.5).
2. **`ARRAY(SELECT ... FROM unnest(...))` 안에서 바깥 LATERAL 별칭 참조 → 500**
   (`missing FROM-clause entry for table "zz"`). 서브쿼리가 새 FROM 스코프를 만들어
   별칭이 보이지 않는다. 같은 값은 **스칼라 컬럼으로 계산**하면 된다(WHERE 절은 이미
   그렇게 쓰고 있다). 발견 즉시 revert했고 영향은 관리자 엔드포인트에 한정됐다.

**교훈**: 진단 코드도 운영에 배포된다. 대상 조건과 SQL 스코프를 본 코드와 같은 기준으로
검토할 것. 배포 후에는 **반드시 응답을 한 번 확인**하고, 실패하면 즉시 되돌린다.
