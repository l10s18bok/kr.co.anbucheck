## 9. 실사용 조건 실측 (2026-08-23, TestFlight 빌드 / 운영 번들)

프로브가 아니라 **실제 구현**(`kr.co.anbucheck.live.HeartbeatNSE`)을 TestFlight로 설치하고
서버 트리거로 검증한 기록.

### 9.1 ★ 엔드투엔드 성공 — 앱이 죽은 채, 탭 없이 전달됐다

세 지점이 독립적으로 일치했다:

```
기기   06:49:53  HeartbeatNSE(Foundation)  [HeartbeatNSE] nse sent
기기   06:49:59  Data Usage HeartbeatNSE — WiFi in/out: 8993/2394
기기   06:50:01  wrote .../AppGroup/.../group.kr.co.anbucheck.live.plist
서버   06:49:53  POST /api/v1/heartbeat 200 OK
서버   06:49:53  NORMAL 발송 완료 → 보호자 폰에 알림 도착(사용자 확인)
```

### 9.2 잠금·화면 꺼짐은 원인이 아니다 (1.8초 만에 실행)

| 발사 | 확장 실행 | 지연 |
|---|---|---|
| 07:01:44 | 07:01:45.8 | 1.8초 |
| 07:11:13 | 07:11:14.8 | 1.8초 |
| 07:12:14 | 07:12:15.9 | 1.9초 |

전부 **잠금 + 화면 꺼짐 2분 이상** 상태. "폰이 자면 푸시를 못 받는다"는 가설은 기각됐다.

### 9.3 ⚠️ 정각 1회 발사는 유실될 수 있다 — APNs 보관 덮어쓰기

06:00 정시 트리거는 **기기에 도달하지 않았다**:

- 성공 문구도 원본 문구도 **둘 다 없었다** (확장이 실패했다면 원본이 떴어야 한다)
- `HeartbeatNSE` 크래시 리포트 **없음**
- 06:15 오프라인 폴백이 **발화**(확장이 제거 경로에 도달 못 함)
- 보호자 폰에 그 시각 알림 **없음** → 서버에 heartbeat가 도달조차 안 함

그런데 **29초 뒤 같은 토큰**으로 보낸 보호자 알림(06:00:39)은 06:01에 정상 표시됐다.
APNs는 기기가 도달 불가일 때 **토큰당 최신 알림 하나만 보관**하므로, 뒤에 온 알림이
보관돼 있던 트리거 푸시를 덮어쓴 것으로 보인다. 밤새 깊은 유휴 + 같은 시각에 겹친
안드로이드 대상자 heartbeat가 조건을 만들었다.

→ **대응: 정각 / +5분 / +10분 재시도**(`job_ios_heartbeat_trigger`).
   첫 성공 시 `last_seen` 갱신으로 자동 중단되고, `apns-collapse-id` 덕에 사용자에게
   보이는 알림은 하나로 대체된다. **연속 2회 발사가 확장을 각각 실행시킴을 실측 확인**
   (9.2) — collapse-id가 후속 전달을 억제하지 않는다.

### 9.4 ⚠️ 발화한 폴백 알림은 pending 제거로 지워지지 않는다

`removePendingNotificationRequests`는 **예약된** 요청만 지운다. 폴백이 이미 발화한 뒤
늦게 안부가 전달되면(재시도 성공·통신 복구) "누르지 않으면 오늘의 안부가 전달되지
않습니다"가 트레이에 남아 **이미 전달된 안부를 두고 거짓 안내**를 한다.
실측: 06:15 발화 → 06:49 전송 성공 → 알림 잔존.
→ `removeDeliveredNotifications`를 함께 호출한다(그날치 식별자 하나뿐이라
§2.5.2 "예약은 건드리지 말 것" 불변 규칙과 충돌하지 않는다).

### 9.5 ⚠️ 진단 도구는 운영 사용자에게 닿을 수 있는 형태로 두지 말 것

즉시 발사 엔드포인트를 만들 때 대상 조건(`supports_push_heartbeat`, `invite_code`)을
빠뜨려 **모든 iOS 기기**가 대상이 됐고, 확장이 없는 **실사용자 22명**에게 일요일 아침
06:40에 "안부 확인이 필요합니다" 알림이 1회 발송됐다(부수효과는 없음 — 구버전엔 확장이
없어 전송·상태 변경이 일어나지 않는다). 진단 쿼리에도 **정규 잡과 동일한 대상 조건을
못박을 것**.

### 9.6 진단 절차 (반복 주기를 하루 → 1분으로)

정규 잡은 "예약시각 정각 + 오늘 미수신"에서만 발화하고, 앱을 열면 2차 안전망이 그날치를
소모해 조건이 깨진다. 그래서 즉시 발사 엔드포인트가 필요하다.

```bash
cd anbucheck-server
curl -s -X POST "$BASE/api/v1/admin/ios-heartbeat-trigger?collapse=true" \
  -H "X-Admin-Key: $(grep '^ADMIN_SECRET_KEY=' .env | cut -d= -f2-)" | python3 -m json.tool
# 응답에 supports_push_heartbeat / is_gs / last_seen / schedule이 함께 나와
# "왜 안 갔는가"를 한 번에 확인할 수 있다.

idevicesyslog -u <UDID> | grep "HeartbeatNSE(Foundation)"   # ⚠️ USB 필수(무선 불가)
```

⚠️ **판독 시 주의**: 성공 알림은 `.passive` + 무음이라 **화면을 깨우지 않는다.**
"알림이 안 왔다"고 판단하기 전에 알림센터를 직접 확인할 것(실제로 한 번 오인했다).

## 10. 이틀 연속 관측 (2026-08-25 / 08-26) — 서버 트리거 실조건

예약시각 06:00, 테스트폰은 책상 위에 두고 밤새 건드리지 않음(셀룰러 없음, 핫스팟 전용).

### 10.1 ★ APNs 보관 규칙이 이 설계의 핵심 제약이다 (문서 근거)

기기가 도달 불가일 때 APNs는 **앱당 최신 알림 하나만 보관**하고, 새 알림이 오면 이전
것을 **버린다**(coalescing). 오래 오프라인이면 보관분도 폐기된다.
→ 정각 1회 발사는 (a) 기기가 그 순간 도달 불가이고 (b) 그 사이 다른 푸시가 오면
**흔적 없이 사라진다.**

### 10.2 8-25 — 망이 아예 없던 날

핫스팟이 꺼져 있었다. 서버는 06:00:03 / 06:05:05 / 06:10:06 **세 번 다 발사**했고
전부 APNs에서 멈췄다. **재시도가 실패한 게 아니라 받을 경로가 없었다** — 이 날 데이터를
재시도 정책의 근거로 쓰면 안 된다.

### 10.3 ★ 8-26 — 딥 슬립 → 물리적 이동으로 깨어난 순간 전달

```
06:00:05  서버 발사 (1회 확인)
          → 폰 딥 슬립 + 핫스팟 → APNs 보관
06:06~08  사용자가 폰을 집어 옮김 → 기기가 깨어나며 APNs 재연결 → 전달
06:09:32  heartbeat 서버 도착 → 보호자에게 알림
```

**앱을 열지도, 알림을 탭하지도 않았는데 안부가 전달됐다.** 기능은 성공이다.
다만 "정시"는 아니었다 — **+9분 32초**. 미수신 체크(+2h)보다는 훨씬 이르다.

⚠️ **여기서 얻은 교훈**: 잠금·화면 꺼짐은 전달을 막지 않는다(§9.2에서 1.8초 실측).
막는 것은 **장시간 유휴로 APNs 연결이 끊긴 상태**이고, 그 상태는 기기가 무언가로
깨어나야 풀린다. 실사용자는 폰을 자주 집으므로 자연히 풀리지만, **탁자에 놓인 채
아무도 건드리지 않는 대상자 폰**은 이 앱의 표준 시나리오다 — 그때 얼마나 걸리는지는
**아직 측정되지 않았다.**

### 10.4 ⚠️ 확장이 **옛 예약시각으로 키를 만든다** (실측 확인)

```
heartbeat_logs:  08-26 06:09:32   key = 2026-08-26_10:00
devices.heartbeat_hour/minute:    06:00   (8-24 16:26 PUT으로 변경됨)
```

App Group의 `hb_hour/hb_minute`가 갱신되지 않아 확장이 **옛 값(10:00)**으로 키를 만들었다.
당시 빌드에는 `armOfflineFallback` 직전 `SharedStore.exportToExtension()`을 호출하는
수정(커밋 `8e39497`)이 **탑재되지 않은 상태**였고, 그 결함이 그대로 드러난 것이다.

날짜는 맞으므로 걸음수 귀속·당일 판정은 정상이지만, **같은 날 앱이 `_06:00` 키로 또
보내면 서버 dedup(키 문자열 일치)이 걸리지 않아 중복 기록이 남는다.**

### 10.5 ⚠️ Railway 로그는 **배포 시작 시점부터만** 보인다 — 두 번 오판했다

로그 화면 상단의 `You reached the start of the range → <시각>`이 **그 배포가 시작된
시각**이다. 그 이전 구간은 `HISTORY`에서 **이전 배포를 열어야** 보인다.

이 함정 때문에 "재시도가 발사되지 않았다"고 두 번 판정했다가 근거가 무너졌다.
**로그를 읽기 전에 항상 range 시작 시각부터 확인할 것.**

또한 **배포는 예약시각(06:00·07:00 등) 근처를 피한다** — 재배포 시 컨테이너가 재시작되며
그 분의 스케줄러 잡이 건너뛰어질 수 있고, 관측이 오염된다.

### 10.6 미결 — 06:05 / 06:10 재시도가 실제로 발사됐는가

8-26에 확인하려 했으나 §10.5의 배포 경계 때문에 결론을 내지 못했다.
`last_seen`은 06:09:32(그날 첫 heartbeat)이고 `recent_logs`에도 그 한 건뿐이므로,
**06:05 시점에 조건(`오늘 미수신`)은 참이었다.** 그렇다면 발사됐어야 한다.
다음 관측에서 **이전 배포 로그까지 포함해** 확인할 것.

### 10.7 진단 도구를 만들다 낸 실수 두 건 (재발 방지)

1. **대상 조건 누락 → 실사용자 22명에게 발송**(§9.5).
2. **`ARRAY(SELECT ... FROM unnest(...))` 안에서 바깥 LATERAL 별칭 참조 → 500**
   (`missing FROM-clause entry for table "zz"`). 서브쿼리가 새 FROM 스코프를 만들어
   별칭이 보이지 않는다. 같은 값은 **스칼라 컬럼으로 계산**하면 된다(WHERE 절은 이미
   그렇게 쓰고 있다). 발견 즉시 revert했고 영향은 관리자 엔드포인트에 한정됐다.

**교훈**: 진단 코드도 운영에 배포된다. 대상 조건과 SQL 스코프를 본 코드와 같은 기준으로
검토할 것. 배포 후에는 **반드시 응답을 한 번 확인**하고, 실패하면 즉시 되돌린다.

1. **키가 `2026-08-27_06:00`인가** → `8e39497`(예약시각 즉시 App Group 반영) 검증

1. 폰을 건드리지 않은 채 **보호자 폰**의 알림을 본다 — 이게 heartbeat 서버 도착의 직접 증거다
2. 한 시간 정도 기다려도 없으면 아이폰 **화면만 터치**(잠금화면 확인). 이 순간 기기가 깨어나며 보관돼 있던 푸시가 전달될 수 있다 — 전달까지 몇 분 걸릴 수 있으므로 5분 정도 본다
3. 그래도 없으면 화면을 연다
4. **앱 실행은 마지막**

### 11.4 터치 없이 쓰는 1차 판별 — 소리 유무

이 푸시는 사일런트가 아니다. 원본은 소리가 나고, **확장이 성공했을 때만** 무음(`.passive`)으로 바뀐다.

- **소리가 났다** → 원본이 표시된 것 = 확장 미실행 또는 전송 실패
- **조용하다** → 확장 성공(무음 전환) **또는** 아직 아무것도 도착 안 함 → 보호자 폰으로 구분

### 11.5 ⚠️ 재시도를 다시 넣지 말 것

+5분·+10분 재시도를 넣었다가 되돌렸다(2026-08-26). 푸시는 잠든 기기를 **깨우지 못한다** —
APNs가 보관했다가 기기가 스스로 깨어날 때 전달되는 것이라, 몇 번을 더 보내도 깨어나는
시점이 달라지지 않는다. 유일한 이득이던 보관 슬롯 재확보도 마지막 재시도 뒤에 다른 푸시가
하나만 더 오면 무력하다. (덮어쓰기 자체는 **APNs의 문서화된 동작**이다 — §13 참조.)
사용자 유도는 오프라인 폴백(+15분)이 이미 보장한다.

|---|---|
| ① 키가 `2026-08-27_06:00`인가 | ✅ **통과** — `8e39497`(예약시각 즉시 App Group 반영) 검증됨. 어제까지 옛 예약시각 `10:00`이 찍히던 문제 해소 |
| ② 전송 성공 시 06:15 폴백 알림이 안 뜨는가 | ❌ **실패** — 06:15에 발화했다. 원인은 race가 아니라 결정적 버그(§12.2) |
| ③ 서버 발사가 06:00 한 줄뿐인가 | ✅ **통과** |

**부수 확인**: 보호자 알림에 `오늘 79보를 걸으셨습니다`가 실렸다 = **확장 안의 CMPedometer가
프로덕션 빌드에서도 동작**한다(프로브에서 본 `steps=34`가 실전 재현).

### 12.1 도달 지연 — n=2

| 날짜 | 발사 | 도달 | 지연 |
|---|---|---|---|
| 08-26 | 06:00 | 06:09:32 | +9분 32초 |
| 08-27 | 06:00:02 | 06:14:52 | **+14분 50초** |

둘 다 딥 슬립 + 사용자 무조작 상태에서 자동 전달됐다. **정시성이 아니라 "언젠가는 온다"가
이 계층이 얻은 것**이며, 그 "언젠가"의 현재 실측 범위가 +9~15분이다.

### 12.2 ★ `rearmOfflineFallback`이 방금 지운 오늘치를 되살린다 (결정적 버그)

06:27 잠금화면 실측 — **전송에 성공했는데도 폴백이 떴다.**

```
06:00  ✅ 안부 전달 완료            ← 확장이 바꿔친 성공 문구
06:15  📶 인터넷 연결 확인          ← 발화하면 안 되는 것
```

NSE 성공 경로(`NotificationService.swift:74-76`)의 순서가 원인이다.

```swift
markSent()                    // hb_last_date = 오늘
clearTodayOfflineFallback()   // 오늘치(06:15) 제거 ✅
rearmOfflineFallback(6, 0)    // ← 같은 ID로 다시 심는다 ❌
```

`rearmOfflineFallback`의 유일한 가드가 `fire > Date()`였는데, 06:14:51 시점에서 오늘치
06:15:00은 **9초 뒤 = 미래**라 offset 0이 통과했다.

⚠️ **이건 타이밍 race가 아니다.** 전송이 폴백 시각(+15분)보다 이른 것이 곧 **정상 성공
케이스**이므로, 성공할 때마다 100% 발동한다. 8/23에 본 "전송했는데 알림이 남아 있다"도
같은 원인이었고, 그때 넣은 `removeDelivered`(`1036e23`)는 **증상만 덮은 것**이었다
(발화 자체를 막지 못하므로 소리·배너는 그대로 나간다).

**수정**: 오늘 전송 마커(`hb_last_date == today()`)가 있으면 재무장 루프에서 offset 0을
건너뛴다. 두 호출부 모두에서 옳다 — 확장(성공 직후, 오늘치 불필요)과 앱
(`armOfflineFallback` 채널; AppDelegate가 직전에 `exportToExtension()`으로
`flutter.last_heartbeat_date`를 복사하므로 값이 최신이다).

### 12.3 진단 엔드포인트의 `fire_times`는 잔재다

`routers/admin_diag.py`가 아직 `fire_0`/`fire_5`/`fire_10` 세 개를 표시한다. **스케줄러 본체는
정각 1회로 고쳐져 있고**(`services/scheduler.py`, §11.5) 동작에는 영향이 없으나, 이 출력만
보고 "재시도가 살아 있다"고 오독할 수 있다. 정리 대상.

### 12.4 ★ 잠금화면 타임스탬프는 **발송 시각**이다 — 전달은 그보다 한참 뒤다

06:27 화면의 `✅ 안부 전달 완료`가 **06:00**으로 찍혀 있는데, 서버가 heartbeat를 받은 것은
**06:14:52**였다. 같은 화면의 `인터넷 연결 확인`은 예약시각(06:15)과 정확히 일치했으므로
표시 로직 자체는 정상이다.

**직접 확증(2026-08-27)**: 잠금화면 그대로 두고 보던 중, **"19분 전"으로 찍힌 알림이
바로 그 순간 화면에 나타났다.** 즉 iOS는 딥 슬립 중 보관된 푸시를 기기가 깨어날 때
전달하면서 **APNs 발송 시각을 그대로 표시**한다.

⚠️ **잠금화면 시각으로 확장이 언제 돌았는지 판단하지 말 것.** 실행 시각의 권위 있는
근거는 서버의 `POST /api/v1/heartbeat` 로그와 `devices.last_seen`뿐이다.

#### 이 비대칭이 폴백 오발화의 구조적 원인이다

| | 정시성 |
|---|---|
| **로컬 알림**(오프라인 폴백) | ⏱ **정확히 예약시각에 발화** (06:15:00) |
| **원격 푸시**(트리거) | 🐢 보관됐다가 기기가 깨어날 때 전달 (+9분·+15분·+19분 관측) |

폴백은 제때 뜨는데 그 폴백을 지워야 할 푸시는 늦게 온다. **+15분은 이 비대칭을 흡수하지
못한다** — 관측 지연이 이미 그 값에 도달했다. §12.2 수정으로 "성공 뒤 되살아나는" 결함은
사라지지만, 도달이 폴백 시각을 넘기면 **한 번 발화한 뒤 나중에 지워지므로 소리·배너는
이미 나간 뒤**다. `offlineDelayMinutes` 상향이 필요한 이유가 여기 있다.

## 13. APNs 보관 슬롯 덮어쓰기 — 가설이 아니라 문서화된 동작

APNs는 기기가 **도달 불가**일 때 그 앱(토픽)의 알림을 **단 하나만** 보관하고, 이후 도착한
알림이 보관된 것을 **교체**한다. `apns-collapse-id`와 무관하고 알림 종류도 가리지 않는다.

**애플 문서·포럼 확인 (2026-08-27)** — 이 동작의 이름은 **coalescing**이다:

> Only one recent notification for a particular app is stored. If multiple notifications are
> sent while the device is offline, **each new notification causes the prior notification to
> be discarded.**
>
> APNs stores a single notification **per topic (bundle ID) per device, regardless of push type.**

출처: [Apple Developer Forums #103527](https://developer.apple.com/forums/thread/103527),
[#765801](https://developer.apple.com/forums/thread/765801)

⚠️ **다만 문서가 말하는 조건은 "offline"이다.** 화면만 꺼진 채 Wi-Fi에 붙어 있는 아이폰이
APNs 기준으로 offline인지는 **문서에 없다** — 판정 기준이 "잠들었는가"가 아니라 **"APNs
지속 연결이 닫혔는가"**이고, 그건 기기·공유기·전파 상태에 좌우된다. 애플은 임계 시간을
문서화하지 않았고 iOS에는 `dumpsys deviceidle` 같은 관측 수단도 없다.
그래서 §14.1 판별 테스트가 필요하다 — **"평범한 수면"이 offline로 취급되는가**가 요점이다.
(참고: 저전력 모드가 켜져 있으면 알림 수신이 추가로 억제된다 — 테스트 시 꺼둘 것.)

이전 판에는 "가설"이라 적어 두었으나 과도한 신중이었다. 우리 트리거 푸시는 **보호자 경고
하나만 뒤에 와도 사라진다** — 이 앱의 G+S 사용자는 동시에 보호자이므로 드문 일이 아니다.

### 13.1 ★ 그래서 오프라인 폴백은 없앨 수 없다

"트리거 푸시가 있으니 폴백은 군더더기 아닌가"라는 판단은 **방향이 반대다.**

```
트리거가 슬롯에서 밀려남  →  NSE가 아예 실행되지 않음
                         →  폴백만이 그날의 유일한 사용자 유도
폴백 제거               →  안부는 조용히 사라지고 보호자만 +2h에 경고를 받는다
```

폴백을 없애면 덮어쓰기가 **무증상 데이터 손실**로 바뀐다. "실패해도 최악이 기존 동작"이라는
이 계층의 설계 전제가 성립하는 근거가 바로 폴백이다. **삭제 검토를 다시 하지 말 것.**

### 13.2 미해결 3건 (2026-08-27 검토)

| # | 내용 | 시급도 |
|---|---|---|
| ① | **자정을 넘어 배달된 어제 트리거가 오늘 슬롯을 먹는다.** 어제 18:00 트리거가 오늘 08:00에 배달되면 NSE가 `오늘_18:00` 키로 전송 → 서버가 당일 안부로 귀속 → 오늘 18:00 트리거는 `last_seen`이 오늘이라 미발사 → **그날 걸음수가 08시까지만** 기록. 안드로이드 `heartbeatPayloadIsFromToday`와 같은 종류의 문제인데 iOS엔 대응이 없다. 수정: 서버 푸시 `data`에 `fire_date`(기기 로컬 날짜)를 넣고, NSE가 `fire_date != today()`면 원본 통과. 필드 부재 시엔 진행(구버전 서버 하위호환) | **프로덕션 전 필수** |
| ② | **스케줄러 tick 1회 누락 = 그날 트리거 소멸.** `date_trunc('minute', now()) = …` 정확 일치 + 단발 + APScheduler 기본 `misfire_grace_time`(1초). 배포·재시작·락 경합으로 그 분을 놓치면 **에러 없이 조용히** 사라진다(`EVENT_JOB_ERROR`는 스킵을 못 잡는다). ⚠️ §11.5의 재시도 반대 논거는 **반복 발송**에만 참이고 **발사 누락**은 다루지 않는다 — 두 실패를 섞지 말 것. 완화책은 폴백 | 다음 릴리스 |
| ③ | `already-sent` 분기가 롤링 7일 창을 갱신하지 않아 앱이 먼저 보낸 날마다 창이 하루씩 소모됐다 | **수정 완료** (`bf20ceb`) |

### 13.3 폴백 지연 권고값 — +45분

관측 상한(+19분)의 2배 이상이면서 보호자 경고(+2h)까지 **75분**을 남긴다. 대상자가 스스로
고칠 창이 실질적으로 확보된다. +90분은 그 창을 30분으로 줄여 이득 대비 손해가 크다.
⚠️ 단 §13.4 테스트에서 "망 복구 후에도 아무것도 안 온다"가 나오면 **상향 자체를 접는다** —
그 경우 폴백이 유일한 경로가 되므로 늦출수록 손해다.

### 13.4 덮어쓰기·망복구를 한 번에 가르는 낮 테스트 (밤샘 불필요)

```
1) 아이폰 비행기 모드
2) admin 트리거 발사 (dry_run=false)              ← 푸시 A: heartbeat_push
3) 삼성폰에서 수동 보고 → 아이폰에 보호자 푸시      ← 푸시 B: 다른 종류
4) 망 복구, 앱은 열지 않는다
5) 알림센터 확인
```

| 결과 | 판정 |
|---|---|
| **B만 도착** | 덮어쓰기 확정 → 폴백 필수 확정 |
| **A·B 모두 도착** | 덮어쓰기 없음 → 폴백 지연 상향에 여유 |
| **아무것도 안 옴** | 망 복구 전달이 안 된다 → 폴백이 유일 경로, 지연 상향 금지 |

오늘 안부가 이미 들어간 뒤라면 A 도착 시 NSE가 `already-sent`로 무음 "안부 전달 완료"를
남긴다 — 도착 여부 판정에는 충분하다.

### 13.5 ★ 덮어쓰기 실측 — 3발 중 **마지막 1발만** 살아남았다 (2026-08-27 10:15, iPhone XS)

§13.4 테스트를 그대로 실행했다.

```
10:15:21  A  트리거 푸시 (heartbeat_push)   ← admin 발사, sent=True
   ~      B  삼성폰 수동 보고 → 보호자 알림
   ~      C  샤오미폰 수동 보고 → 보호자 알림   ← 마지막
10:2x     비행기 모드 OFF (화면 켠 채 대기)
10:50     28분 경과 — 잠금화면에 **C만** 있다. A·B는 오지 않았다
```

| 판정 | 결과 |
|---|---|
| APNs 보관 슬롯 | **1칸** — 확정 |
| 알림 종류 구분 | **없음** — 보호자 알림이 heartbeat 트리거를 밀어낸다 |
| `apns-collapse-id` | 무관 — 서로 다른 id끼리도 밀어낸다 |
| 지연 도착 | 없음. 밀려난 것은 **영구 소실**이다 |

⚠️ **이 앱의 iOS 사용자에게 이 충돌은 구조적이다.** iOS는 보호자 전용 + G+S이므로
**heartbeat를 보내는 iOS 기기는 예외 없이 보호자이기도 하다.** 즉 대상자들의 안부 알림이
매일 같은 아침 시간대에 자기 트리거와 슬롯을 다툰다.

**대조군 (11:14)**: 망이 있고 기기가 깨어 있는 상태에서 같은 트리거를 다시 쏘자
`✅ 안부 전달 완료`가 즉시 도착했다. **전송 경로는 멀쩡하다** — 10:15의 A가 오지 않은
원인은 덮어쓰기 하나로 좁혀진다.

**그리고 이것이 §13.1(폴백 존치)의 실측 근거다.** 트리거가 밀려난 날 NSE는 아예 실행되지
않으므로, 폴백이 없으면 그날 안부는 **아무 신호 없이** 사라진다.

## 14. 덮어쓰기 대책 — 재발사가 아니라 **피기백**이다 (설계 결정, 2026-08-27)

§13.5로 덮어쓰기가 확정된 뒤 두 안을 비교했다.

### 14.1 ⚠️ 먼저 — §13.5는 **비행기 모드**였다. 실제 실패 모드는 딥 슬립이다

오늘 테스트는 진짜 오프라인(비행기 모드)에서 재현했다. 그런데 실사용의 실패 모드는
**딥 슬립**이고, 딥 슬립 아이폰은 Wi-Fi로 APNs 연결을 유지한 채 **표시만 미루는 것**일
수도 있다. 그렇다면 슬롯 경쟁이 아예 일어나지 않고, 아래 대책의 가치가 크게 준다.

8/23 관측(트리거 소실 + 29초 뒤 보호자 알림 도착)이 딥 슬립 사례지만 **n=1이고 교란이 있다.**

**판별 테스트 — §13.4와 딱 한 가지만 다르다:**

```
비행기 모드를 쓰지 않는다. 화면을 끄고 20분 이상 방치해 딥 슬립에 넣는다.
→ A(트리거) → B(대상자1 수동보고) → C(대상자2 수동보고)
→ 폰을 집어 깨우고 잠금화면 확인

셋 다 보임  → 딥 슬립에서는 덮어쓰기 없음 → 피기백 우선순위 급락
C만 보임    → 딥 슬립에서도 덮어쓰기 → 피기백 도입 확정
```

⚠️ **이 결과를 모르고 서버·클라를 바꾸면 일어나지도 않는 문제를 위해 복잡도를 늘리게 된다.**

### 14.2 기각안 — 트리거 주기 재발사 / 이벤트 기반 재발사

| 안 | 기각 사유 |
|---|---|
| **15분 간격 8회** | 밀려났는지 모른 채 맹목 발사. 대부분 헛발이고 사용자 기기를 불필요하게 깨운다 |
| **이벤트 기반 재발사**(다른 푸시 직후 트리거 재발사) | ① `heartbeat_service.py` / `emergency_service.py`가 `asyncio.gather`로 팬아웃해 **재발사가 다른 알림보다 먼저 APNs에 닿을 수 있다** → 다시 밀려나 무효. ② 훅 지점이 4곳(heartbeat/emergency/alert/scheduler)이라 **푸시 종류가 늘면 커버리지가 조용히 샌다** |

### 14.3 ★ 채택 방향 — 밀어낸 놈을 트리거로 쓴다 (추가 발송 0)

서버는 `push_service.send_push`에서 **모든** 푸시에 `mutable_content=True`를 붙인다.
따라서 **확장은 보호자 알림에서도 이미 깨어난다** — 지금은 type 게이트가 원본을 즉시
통과시킬 뿐이다. 그 게이트를 3분류로 바꾼다:

```
heartbeat_push                          → 기존 동작 (성공 시 "전달 완료"로 치환)

auto_report / manual_report / steps /   → ★ 오늘 미전송 && 예약시각 지났으면
battery_low / battery_dead /               heartbeat를 조용히 보내고,
alert_resolved / alert_cleared             알림 내용은 **원본 그대로** 배달

alert_caution / alert_warning /         → 즉시 원본 통과 (기존과 동일)
alert_urgent / emergency /                 ⚠️ 네트워크 대기 절대 금지
subscription_*
```

**어느 푸시가 살아남든 안부가 나간다 → 덮어쓰기가 무해해진다.**

| | 이벤트 재발사 | 피기백 |
|---|---|---|
| 추가 발송 | 충돌당 1회 | **0** |
| 순서 경쟁 | 취약 | 무관 |
| 훅 지점 | 서버 4곳 | 없음 (클라 ~15줄) |
| 서버 변경 | 필요 | **불필요** |
| 자정 넘김(§13.2 ①) | 별도 대응 필요 | 게이트가 "오늘" 기준이라 구조적 면역 |
| tick 누락(§13.2 ②) | 미해결 | 그날 다른 푸시가 흡수 |

**불변 규칙 둘 — 주석으로 못 박을 것:**
1. **긴급 계열은 절대 지연시키지 않는다.** 허용목록(allow-list) 방식으로 구현하고 기본은
   즉시 통과 — 새 type이 추가돼도 안전한 쪽으로 떨어진다.
2. **피기백 성공 시 알림 본문을 건드리지 않는다.** 보호자 경고 문구가 훼손된다.

**남는 위험**: 보호자 알림 여러 건이 거의 동시에 도착하면 확장 인스턴스가 병렬로 떠
**중복 전송**이 가능하다(iOS 확장에는 안드로이드의 SQLite 락에 해당하는 것이 없다).
서버 `is_first_today` 판정 덕에 `auto_report` 중복 푸시까지 가지는 않겠지만
`heartbeat_logs`에 행이 둘 생길 수 있다. App Group에 in-flight 마커(타임스탬프 + 짧은
TTL)를 두면 대부분 막힌다.

### 14.4 반영 순서 — 검증 빌드에 새 설계를 얹지 않는다

```
이번 빌드   폴백 되살아남 수정(5ab2db9) + already-sent 재무장(bf20ceb)
            + 폴백 지연 45분 + 예약시각 가드
            → TestFlight → 다음 날 아침 실전 검증

그 사이     §14.1 판별 테스트(딥 슬립 덮어쓰기)

다음 빌드   결과가 "C만"이면 피기백 도입
```

덮어쓰기 대책이 없어도 최악은 폴백이 뜨는 것이고, 그건 §13.1에서 존치가 확정된 안전망이다.

### 14.5 자정 넘김(§13.2 ①) — `fire_date` 대신 클라 가드로 해결했다

어드바이저 제안은 서버 푸시 `data`에 `fire_date`를 실어 확장이 대조하는 것이었으나,
**클라 단독으로 같은 결과가 나온다** — `HeartbeatStore.scheduledTimePassed()`로 "지금이
오늘 예약시각을 지났는가"만 보면 된다.

- 어제 18:00 트리거가 오늘 08:00 배달 → `08:00 < 18:00` → **전송하지 않고 원본 통과**
- 오늘 06:00 트리거가 06:14 배달 → `06:14 >= 06:00` → 정상 전송
- 늦은 배달(예: 06:00 트리거가 07:00 배달)도 오늘 몫이 맞으므로 통과

서버 변경이 없어 배포 순서에 얽매이지 않고, 구버전 서버와도 무관하다.

### 14.6 ★★ 판별 테스트 결과 — **평범한 수면도 APNs 기준 offline이다** (2026-08-27 13:21)

§14.1이 요구한 테스트를 그대로 실행했다. **§13.5와 다른 점은 비행기 모드를 쓰지 않은 것뿐이다.**

```
11:57~13:21  아이폰 방치 (앱 스와이프 킬, 화면 off, USB 분리, 저전력 모드 off)
                         ↑ 83분. 비행기 모드 아님 — Wi-Fi 정상 연결 상태
13:21:27  A  트리거 푸시 발사 (sent=True, 갱신된 토큰 fCO5BMoX0U…)
13:24     B  삼성폰 [🚨 도움이 필요해요] → 아이폰(보호자)에 긴급 알림
13:26     화면 켬 → ★ **긴급(B)만 보인다. A는 없다.**
```

| 질문 | 답 |
|---|---|
| 화면 끈 아이폰이 APNs 기준 offline인가 | ✅ **그렇다** — 보관·덮어쓰기가 일어난다 |
| 덮어쓰기가 실사용 조건에서 일어나는가 | ✅ **일어난다.** 비행기 모드 같은 인위적 조건이 아니다 |
| 밀려난 트리거의 지연 도착 | ❌ 없음. **영구 소실** |

⚠️ **이로써 §14.3 피기백 도입이 확정됐다.** 트리거 푸시 하나에만 의존하면, 그 기기로 다른
알림이 하나만 더 가도 그날 안부가 조용히 사라진다. iOS 사용자는 전원 보호자이기도 하므로
이 충돌은 예외가 아니라 일상이다.

**08-27 아침 성공(06:00 발사 → 06:14 전달)은 운이 좋았던 것이다** — 삼성폰 안부가 07:29에
와서 그 14분 창이 비어 있었을 뿐이다. 대상자의 예약시각이 보호자 자신의 예약시각보다
이르면 매일 밀려난다.

### 14.7 이 결과가 확정하는 것 / 확정하지 않는 것

- ✅ **폴백 존치** — 트리거가 밀려난 날 NSE는 실행조차 안 되므로 폴백만이 유일한 신호다(§13.1)
- ✅ **피기백 도입** — 어느 푸시가 살아남든 안부가 나가야 한다(§14.3)
- ⚠️ **여전히 미확정**: 몇 분 만에 offline 상태가 되는지. 83분은 충분했고 그 이하는 미측정.
  애플이 임계값을 문서화하지 않았고 iOS에 관측 수단이 없으므로 **알 수 없다고 두는 것이 맞다.**

## 15. 피기백 구현 완료 + 다음 관측 (2026-08-27 저녁 → 08-28 아침)

### 15.1 이번 빌드에 들어간 것 (`0b487e0` 외)

| 커밋 | 내용 |
|---|---|
| `5ab2db9` | 전송 성공 후 오프라인 폴백이 **되살아나던** 결함 (재무장이 방금 지운 오늘치를 다시 심음) |
| `bf20ceb` | `already-sent` 분기에서도 롤링 7일 창 재무장 |
| `ab3f7f6` | 폴백 지연 15 → **45분** + `scheduledTimePassed` 가드(자정 넘긴 트리거 차단) |
| `0b487e0` | **피기백** + 중복 전송 방지 in-flight 마커 + **`_onHeartbeatSent`의 iOS 폴백 제거** + 진단 로그 |

**서버 변경 없음.** 피기백이 가능한 이유가 서버가 이미 모든 푸시에 `mutable_content=True`를
붙이고 있어서다 — 확장은 원래부터 보호자 알림에서도 깨어나고 있었고, type 게이트가 원본을
통과시켰을 뿐이다. 이미 열린 문을 쓰는 것이라 서버에 추가할 것이 없다.

#### ⚠️ 폴백을 지우는 경로가 하나뿐이었다 (같은 결함의 두 번째 얼굴)

`5ab2db9`는 **확장 경로**를 고쳤지만, **앱이 안부를 보낸 날**은 여전히 아무도 지우지 않았다.
`_onHeartbeatSent`는 `cancelSendFailed`/`cancelSubjectSafetyNet`만 부르고 iOS 폴백은
건드리지 않았다. 그래서:

```
06:00  트리거 발사 → 밀려남
06:20  사용자가 앱을 엶 → 대시보드가 안부 자동 전송 ✅
06:45  ★ "인터넷 연결 확인" 발화 — 망도 있고 안부도 갔는데
```

⚠️ **재무장의 `sentToday` 스킵으로는 못 막는다 — 다시 심지 않는 것과 이미 심긴 것을 지우는
것은 다르다.** 채널 메서드 `clearOfflineFallbackToday`를 추가해 `_onHeartbeatSent`에서 부른다.

### 15.2 ⚠️ `flutter install`은 **삭제 후 재설치**다

`Uninstalling old version...`이 찍힌다. 업데이트 설치가 아니므로 **App Group이 통째로
지워진다** — `nse_last_log`·`hb_last_date`·심어둔 폴백 알림이 전부 사라진다.
사후 포렌식(확장이 돌았는지)을 하려면 **설치 전에** 값을 뽑아 둬야 한다.
(2026-08-27에 이걸 모르고 설치해 13:21 판정의 양성 증거를 잃었다. 결론 자체는
11:14 대조군으로 유지된다.)

⚠️ **다만 "재설치했으니 검증이 무효"로 넘겨짚지 말 것** (2026-08-28 정정). 지워지는 것은
App Group의 **과거 진단 기록**(`nse_last_log` 등)이지 앞으로의 테스트가 쓸 값이 아니다.
새 커밋이 NSE·피기백·폴백·알람·heartbeat 경로를 건드리지 않았다면 검증 대상 코드는 그대로이므로
**그 빌드로 테스트를 이어가면 된다.** 판단 근거는 설치 방식이 아니라 **diff 범위**다.

✅ **개발 서명 빌드도 푸시가 정상 도달한다 — 실측**(2026-08-28). `flutter build ios --release`
산출물은 `aps-environment: development`(sandbox APNs)라 TestFlight(production)와 환경이 다르지만,
**아이폰 앱을 스와이프 킬한 상태에서 안드로이드 대상자의 안부 → 보호자 알림이 정상 도착**했다.
Firebase가 sandbox 토큰을 정상 처리한다는 뜻이므로 **푸시 테스트를 위해 TestFlight로 되돌릴
필요가 없다.** (확장도 `Runner.app/PlugIns/HeartbeatNSE.appex`로 정상 번들된다 —
`codesign -d --entitlements - --xml <app>`으로 `aps-environment`를, `ls PlugIns/`로 확장 포함을 확인.)

### 15.3 진단 수단 — 이제 확장 실행 여부를 사후에 알 수 있다

앱 실행 시 `NSLog("[HeartbeatNSE] last=%@", nse_last_log)`가 찍힌다. 값에 타임스탬프가
포함되므로 **"언제 무엇을 했는지"**가 남는다.

```
sent          전송 성공
already-sent  오늘 이미 전송돼 통신 생략
locked        다른 확장 인스턴스가 전송 중
before-schedule  예약시각 이전 — 자정 넘겨 배달된 어제 트리거
no-credentials / send-failed / budget / expired
```

⚠️ `flutter logs`로는 네이티브 NSLog가 안 잡히는 경우가 있다. USB 연결 후
`idevicesyslog | grep HeartbeatNSE`가 확실하다.

### 15.4 08-28 아침 관측 — 한 번에 네 가지를 판정한다

```
06:00  서버 트리거 발사 (자동)
06:02  삼성폰에서 [지금 안부 보고하기]      ← 트리거를 밀어낸다(§14.6 재현)
  ~    아이폰은 계속 재운다 (건드리지 않음)
       깨는 순간 manual_report 배달 → ★ 피기백이 안부를 전송해야 한다

```

| 판정 대상 | 통과 조건 |
|---|---|
| **피기백** | 트리거가 밀려났는데도 `last_seen`이 08-28로 갱신된다 |
| 폴백 되살아남(`5ab2db9`) | 06:45에 "인터넷 연결 확인"이 뜨지 않는다 |
| 폴백 45분(`ab3f7f6`) | 위와 같음 |

⚠️ **긴급이 아니라 수동 보고를 써야 한다.** 긴급·경고 계열은 피기백 허용목록에서
의도적으로 제외돼 있다(네트워크 대기가 긴급 알림을 늦추면 안 되므로). 긴급으로 테스트하면
피기백이 발동하지 않아 아무것도 검증되지 않는다.

⚠️ 삼성폰 수동 보고는 **하루 1회 제한**이 있다. 08-28에 아직 안 썼는지 확인할 것.

### 15.5 ★ 08-28 관측 결과 — 폴백 오발화 해소 확인, 피기백은 미검증

```
06:00:0x  서버 트리거 발사 (자동)
06:02:54  POST /api/v1/heartbeat 200 — key `2026-08-28_06:00`   ← 지연 +2분 54초
06:03:15  admin으로 manual_report 발사 (삼성폰을 깨우지 않으려고 서버에서 직접)
06:20     화면 켬 → 잠금화면에 **두 알림이 모두** 보인다
06:45     ★ 폴백 발화 없음 — 소리도 없었다
06:51     재확인 — 여전히 없음
```

| 판정 | 결과 |
|---|---|
| 트리거 → NSE → 전송 (앱 미실행) | ✅ 키 정확, **지연 +2분 54초로 역대 최단** |
| 폴백 되살아남(`5ab2db9`) + 앱 경로 제거 + 45분(`ab3f7f6`) | ✅ **통과** — 어제 같은 조건에서 06:15에 떴던 것이 오늘은 안 떴다 |
| 예약시각 가드(`scheduledTimePassed`) | ✅ 정상 경로를 막지 않음 |
| 피기백 본문 불변 규칙 | ✅ "수동 안부 확인"이 원본 그대로 표시 |
| **피기백 본체** | ❌ **미검증** |

**피기백이 검증되지 못한 이유**: 트리거가 밀려나지 않았다. 06:00 발사분이 **06:02:54에 이미
도착**해 안부가 나갔고, 06:03:15의 manual_report는 `already-sent`로 통신 없이 끝났다.
잠금화면에 두 알림이 **다 보이는 것**이 덮어쓰기가 없었다는 증거다 — 이 날 폰은 어제만큼
깊이 잠들지 않았다.

⚠️ **딥 슬립 진입 여부는 통제할 수 없다.** §14.6은 83분 방치로 재현됐지만 오늘은 같은
조건에서 재현되지 않았다. 피기백 검증은 **비행기 모드로 강제**해야 결정적이다:

```
(전날 밤)  아이폰 비행기 모드 ON, 앱 킬
예약시각    자동 트리거 발사 → APNs 보관 (도달 불가)
+5분       admin으로 manual_report 발사 → 트리거를 밀어냄
+7분       비행기 모드 OFF
           → manual_report만 배달 → ★ 피기백이 안부를 보내야 한다
```

⚠️ 조건 하나: **그날 안부가 아직 나가지 않았어야 한다**(`last_seen < 오늘 자정`).
이미 전송된 날에는 `already-sent`로 끝나 아무것도 검증되지 않는다.

### 15.6 ⚠️ 배포가 로그 경계를 만들었다 (§10.5 재발)

06:02:16에 진단 옵션을 배포해 06:03:05에 새 컨테이너로 넘어갔는데, heartbeat 도착이
**06:02:54**였다. 그래서 `POST /api/v1/heartbeat`와 보호자 알림 발송 로그가 **이전 배포**에
남아 현재 로그에서 사라진 것처럼 보였다. 06:00 트리거 발사 줄도 마찬가지다.
**예약시각 근처 배포는 관측을 이렇게 망친다.**

## 16. ⚠️ 피기백이 **순수 보호자 기기에서 오발동**하던 결함 (프로덕션 배포 전 발견)

"기존 iOS 사용자가 업데이트하면 문제가 없는가"를 검토하다 발견했다.

### 16.1 무엇이 잘못됐나

```
순수 보호자(G+S 아님)가 auto_report 푸시를 받는다   ← 매일, 대상자 수만큼
  → 확장이 깨어남 (서버가 모든 푸시에 mutable_content를 붙이므로)
  → 피기백 허용목록에 든 타입 → 통과
  → lastSentDate 가 빈 값 → "오늘 안 보냈다"로 판정   ← 보호자는 원래 안 보낸다
  → 예약시각은 App Group에 없어 **기본값 18:00** → 저녁 이후면 통과
  → ★ 보호자 기기가 자기 heartbeat 를 서버로 전송한다
```

**트리거 푸시만 있을 때는 안전했다** — 서버가 `u.invite_code IS NOT NULL`(G+S)에게만
보냈기 때문이다. **피기백은 그 게이팅을 우회한다.** 얹히는 대상이 *모든 보호자에게 가는
알림*이라, 서버 쪽 조건이 아무 역할도 하지 못한다.

증상: 보호자 기기의 불필요한 통신, `heartbeat_logs`에 대상자가 아닌 기기의 기록,
`devices.last_seen` 오염.

### 16.2 수정 — App Group에 "보내는 쪽인가"를 실어 보낸다

App Group에는 대상자 여부를 알 수단이 **하나도 없었다**(device_token·device_id·서버주소·
예약시각·마지막 전송일·번역 문구뿐). `flutter.invite_code`의 존재 여부를
`hb_is_subject`로 내보내고, 확장이 그것을 요구한다.

```swift
guard store.isSubject else { finish(success: false, note: "not-subject"); return }
```

- **invite_code로 판정하는 이유**: G+S와 순수 대상자를 모두 포착하고 순수 보호자만 제외된다.
- **기본값은 false**다. 값이 없으면 *보내지 않는 쪽*으로 떨어져야 한다 — 잘못 보내는 것이
  안 보내는 것보다 나쁘다. 구버전 App Group에는 이 키가 없으므로 이 기본값이 곧 안전장치다.
- 트리거 경로는 서버가 이미 게이팅하지만 같은 가드를 공유한다(이중 방어).

### 16.3 교훈 — 게이팅의 주체가 바뀌면 조건도 따라가야 한다

트리거 시절의 안전은 **서버가 대상을 골랐기 때문**이었다. 피기백은 "이미 나가는 푸시에
얹는" 설계라 대상 선택권이 서버에서 **확장으로 넘어왔다.** 그러면 서버가 하던 판정을
확장이 이어받아야 하는데, 그 이관이 빠져 있었다. **전달 경로를 바꿀 때는 그 경로가
암묵적으로 의존하던 조건이 무엇이었는지 먼저 적어 볼 것.**

### 16.4 부분 검증 — 게이트·`isSubject` 가드가 정상 동작한다 (2026-08-29 05:52)

`1.2.9+53`(main 통합본) 설치 직후, 오늘 안부가 이미 나간 상태에서 `manual_report`를 쏴
**전송 직전까지의 경로**를 확인했다. USB + `idevicesyslog`로 실시간 관측.

```
05:52:40      서버가 manual_report 발사 (admin, push_type=manual_report)
05:52:41.384  확장 로드 — HeartbeatNSE(1.2.9)
05:52:41.422  [HeartbeatNSE] nse already-sent      ← 0.04초 만에 판정
```

| 판정 | 근거 |
|---|---|
| 확장이 실행됨 | 로그 존재 |
| **피기백 게이트가 `manual_report`를 통과시킴** | 게이트에서 즉시 반환하면 **로그가 아예 없다**(그 분기는 `HeartbeatStore.log`를 부르지 않는다) |
| **`isSubject` 가드가 대상자 기기를 막지 않음** | `not-subject`가 아니다 → `hb_is_subject` 브리지 정상 |
| App Group 자격증명 전달 | `no-credentials`가 아니다 |
| 본문 불변 규칙 | 잠금화면에 "수동 안부 확인" 원본 그대로 |

**로그 문자열이 판정을 가른다는 점이 핵심이다.** 각 분기가 서로 다른 note를 남기도록 만들어
둔 덕에, 전송이 일어나지 않는 상황에서도 어디까지 갔는지 정확히 알 수 있다.

⚠️ `idevicesyslog` 판독 시: 우리 로그의 프로세스명은 **`HeartbeatNSE(Foundation)`**이다.
`grep -i heartbeatnse`로는 `runningboardd`·`PerfPowerServices`의 시스템 잡음이 압도하므로
**`grep -F "[HeartbeatNSE]"`**로 우리 NSLog만 뽑을 것. (`-i`로 `locked`를 찾으면 시스템의
`Locked`가 대량으로 걸린다 — 실제로 한 번 오독했다.)

**남은 것은 실제 전송 한 단계뿐이다.** 조건("오늘 안부 미전송")을 만들려면 밤새 비행기
모드가 가장 확실하다 — 망이 없으면 실수로 앱을 열어도 전송이 실패해 `lastHeartbeatDate`가
박히지 않으므로 조건이 유지된다(08-29 새벽에 앱이 포그라운드로 올라와 00:22에 전송되는
바람에 그날 테스트를 통째로 날렸다).

## 17. ★★ 피기백 종단 검증 성공 (2026-08-30 00:13, iPhone XS / 1.3.1+54)

트리거를 **의도적으로 밀어낸 뒤**, 살아남은 보호자 알림이 안부를 실어 나르는 것을 확인했다.

```
(전날) 예약시각을 00:10으로 변경 → 앱 킬 → 비행기 모드 ON
00:10:05  서버 트리거 자동 발사 (heartbeat_push) → APNs 보관 (도달 불가)
00:13:14  admin 으로 manual_report 발사 → 보관 슬롯을 덮어씀 → ★ 트리거 소멸
  ~       비행기 모드 OFF → manual_report **만** 배달
00:13:51  확장 실행 — HeartbeatNSE(1.3.1)
00:13:51  POST /api/v1/heartbeat 200 — key `2026-08-30_00:10`
00:13:52  [HeartbeatNSE] nse sent          ← 전송 성공 경로에서만 찍힌다
00:13:54  보호자 알림 2건 발송
00:13:57  확장 종료 (총 6초)
```

| 판정 | 결과 |
|---|---|
| **피기백 본체** | ✅ **성공** — 트리거가 아닌 푸시(`manual_report`)가 안부를 전송했다 |
| 예약시각 키 | ✅ `2026-08-30_00:10` — `scheduledTimePassed` 가드 통과 후 정확한 키 |
| `isSubject` 가드 | ✅ 대상자 기기를 막지 않음 |
| 응답 속도 | 배달 → 전송 완료까지 **1초 미만**, 확장 총 수명 6초 |

**판정을 가른 것은 로그다.** 서버의 `last_seen`만으로는 "누가 보냈는지"를 알 수 없다 —
앱이 보냈을 수도, 확장이 보냈을 수도 있다. `[HeartbeatNSE] nse sent`가 확장의 전송 성공
경로에서만 찍히기 때문에 확정이 가능했다. **분기별로 다른 note를 남기도록 만들어 둔 것이
이 검증을 가능하게 했다.**

### 17.1 이로써 iOS 계층이 완성됐다

```
예약시각 정각  →  트리거 푸시 → NSE가 탭 없이 전송              (§12 검증)
트리거가 밀림  →  살아남은 보호자 알림에 얹혀 전송              (§17 검증 ← 여기)
망 자체가 없음 →  오프라인 폴백(+45분)이 사용자에게 알림        (§13.1 존치 확정)
```

APNs 슬롯이 앱당 1칸이라는 구조적 제약(§13.5·§14.6)에 대한 대책이 실제로 동작함이
확인됐다. **iOS 사용자는 전원 보호자를 겸하므로 이 충돌은 일상이며**, 피기백이 없으면
그런 날의 안부는 아무 신호 없이 사라진다.

### 17.2 ✅ 잠금화면 확인 — 본문 불변 + 덮어쓰기 직접 증거

전송 직후 잠금화면에 **`✅ 수동 안부 확인` 하나뿐**이었다. 두 가지가 동시에 확인된다.

| 관측 | 의미 |
|---|---|
| 본문이 원본 그대로 | ✅ **피기백은 문구를 건드리지 않는다**는 불변 규칙 준수. `안부 전달 완료`로 바뀌었다면 규칙 위반이다 |
| 트리거 알림이 **없다** | ✅ 덮어쓰기가 실제로 일어났다는 **직접 증거**. 트리거가 살아 있었다면 `안부 전달 완료`가 함께 보였을 것 |

즉 이 한 장면이 **"밀려났는데도 안부는 전달됐다"**를 그대로 보여준다 — 이 설계가 노린 상황이다.

## 18. iOS도 `suspicious`를 판정할 수 있는가 — 분석과 측정 계획 (2026-08-31, 미해결)

### 18.1 현재 상태

**iOS는 `suspicious=true`를 만들지 않는다.** 전송 경로 넷이 전부 `false`로 귀결된다.

| 경로 | 값 |
|---|---|
| 확장(NSE) — 트리거·피기백 | `false` **하드코딩** |
| 앱 포그라운드 자동 전송 | `isInteractiveAtTrigger: true` → false |
| 수동 보고 | `manual: true` → false |
| 회복 전송 | `recovery` → false |

즉 **걸음수가 0이어도 보호자에게 "활동 기록 없음" 경고가 가지 않는다.** 안부 자체가
안 오는 경우(미수신)는 서버 스케줄러가 정상적으로 경고하므로, 빠진 것은 *"안부는 왔는데
하루 종일 활동 증거가 없다"* 한 가지다.

⚠️ **서버는 전송 경로를 모른다.** 페이로드에 `device_id·timestamp·manual·steps_delta·
suspicious·battery_level·scheduled_key`뿐이고 `src`는 클라 logcat 전용이다. 서버가 받는
것은 클라가 이미 접어 넣은 `suspicious` 불리언 하나다.

### 18.2 안드로이드의 신호는 생각보다 부실하다

안드로이드는 `ScreenState.isInteractive()`(= `PowerManager.isInteractive()`, 화면 켜짐)를
suspicious 판정 2순위로 쓴다. 그런데 이 신호에는 결함이 둘 있다.

**① 화면 켜짐은 사람이 조작했다는 증거가 아니다.** 알림 하나로 화면이 켜져도 참이 된다 —
사람이 아무것도 하지 않아도 "활동 있음"으로 구제된다.

**② 판정이 우연에 좌우된다.** `suspicious=false`가 되는 경로가 둘인데 성질이 다르다.

```
① 앱 실행       → execute(isInteractiveAtTrigger: true) 하드코딩. 결정적
② 폰 사용만     → 워커가 실측. 그런데 Doze 해제 후 발화까지 2분50초~9분 걸린다
                  (실측: 08-16 +8분43초 / 08-18 +2분50초 / 08-18 +9분)
                  → 폰을 10분 쓰면 구제되고 30초 쓰면 구제되지 않는다
```

게다가 **그날 먼저 전송한 경로가 결과를 확정한다.** 18:05에 Doze 워커가 `true`로 보내
경고가 나간 뒤 18:30에 사용자가 폰을 집어도 되돌릴 방법이 없다.

### 18.3 iOS에서 쓸 수 있는 신호 4가지

앱이 살아 있으면 상태를 우리가 안다. **문제는 앱이 스와이프 킬된 상태 — 확장만 도는 경우다.**

| # | 신호 | 확장에서 가능? | 성질 |
|---|---|---|---|
| ① | **앱이 오늘 포그라운드에 떴는가** (App Group 마커) | ✅ 자명 | 하루 단위. 결정적. 새 API·권한 불필요 |
| ② | **잠금 해제 상태인가** (키체인 프로브) | ✅ 문서화됨 | 순간 스냅샷. **증거로는 가장 강함** |
| ③ | **움직임 이력** (`CMMotionActivityManager.queryActivityStarting`) | ⚠️ 미검증(같은 CoreMotion인 `CMPedometer`는 확장에서 동작 확인됨) | 하루 단위 소급 조회 |
| ④ | **APNs 도착 지연** (`지금 − 오늘 예약시각`) | ✅ 계산만 하면 됨 | 간접 프록시. 서버 변경 불필요 |

**②의 원리**: `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` 항목은 잠금 상태에서 접근이
거부된다(`errSecInteractionNotAllowed` = -25308). 확장이 **자기 access group에** 직접 쓰고
읽으면 되므로 앱의 도움도, 키체인 공유 entitlement도 필요 없다.

### 18.4 ★ 잠금 해제가 화면 켜짐보다 나은 신호다

```
화면 켜짐   →  사람이 켰을 수도, 알림이 켰을 수도 있다        (약함)
잠금 해제   →  Face ID(주시 필요) 또는 암호 입력이 있었다      (강함)
```

**안드로이드의 `isInteractive`가 오히려 부실하다.** iOS를 안드로이드에 맞추는 게 아니라,
안드로이드를 `KeyguardManager.isKeyguardLocked()`로 바꾸면 **양쪽이 같은 의미의 신호**를
쓰게 되고 "알림 때문에 화면만 켜진" 오탐도 사라진다. — 별건 후보.

### 18.5 ⚠️ 방향이 비대칭이다 — 구제 조건으로만 쓸 것

②③④ 모두 **한쪽 방향만 정확하다.**

```
해제됨/움직임 있음/빨리 도착  →  사람이 활동했다        (강함)
잠금/정지/늦게 도착          →  "지금 안 만지고 있다"   (약함 — 30분 전은 모른다)
```

그래서 판정에 넣을 때는 이 형태여야 한다.

```
suspicious = false  ←  걸음수 > 0
                   또는 잠금 해제 상태였다
                   또는 오늘 앱이 포그라운드에 떴다
                   또는 (검토) 도착 지연 < N분
suspicious = true   ←  그 외
```

**구제 조건만 더하면 경고가 늘지 않고 줄기만 한다.** 반대로 "늦게 도착 → 활동 없음"처럼
쓰면 전파 상태 때문에 거짓 경고가 난다.

### 18.6 ⚠️⚠️ **이 절의 추론은 2026-09-01에 반증됐다** — §18.20을 먼저 읽을 것

아래는 "iOS 확장은 예약시각 정각에 실행되므로 그 순간 잠겨 있을 확률이 높다"는 전제로
쓴 것인데, **그 전제가 틀렸다.** 확장은 정각에 돌지 않는다 — 푸시는 APNs에 보관됐다가
**기기가 깨어날 때** 배달되고(실측 +2분54초 / +9분32초 / +14분50초), 기기를 깨우는 것은
대개 사용자가 폰을 집어 드는 행위다(§10.3). 즉 안드로이드의 "Doze가 풀릴 때 워커 발화"와
**같은 메커니즘**이다. 기록을 위해 남기되 근거로 쓰지 말 것.

### 18.6 (반증됨) ②를 안드로이드 방식 그대로 이식하면 오히려 나쁘다

발화 시점이 다르기 때문이다.

```
안드로이드  워커가 Doze에 막혀 있다가 **사용자가 폰을 켤 때** 풀려 발화
            → 그 순간 화면 켜짐인 경우가 흔하다 → false 가 잘 나온다

iOS        확장은 서버 푸시로 **예약시각 정각에** 실행된다
            → 19:00 정각에 폰이 잠겨 있는 게 정상이다 → true 가 쏟아진다
```

안드로이드 신호가 그나마 작동한 이유가 **"늦게, 사용자가 깨울 때 뛴다"는 결함 덕**이었다.
그래서 ②는 단독 판정이 아니라 **①③④와 함께 구제 조건으로** 쓸 때만 의미가 있다.

### 18.7 측정 계획 — 판정은 바꾸지 않고 로그만 남긴다

브랜치 `probe/ios-lock-signal`. **`suspicious`는 여전히 `false` 고정이며 동작은 하나도
바뀌지 않는다.** 확장이 실행될 때마다 아래를 `nse_last_log`에 남긴다.

```
nse sent unlocked=Y lag=3m type=trigger steps=42
         │          │       │              └ 걸음수
         │          │       └ 트리거인가 피기백인가 (피기백이면 lag은 무의미)
         │          └ 예약시각 대비 도착 지연(분)
         └ 잠금 해제 여부 (Y/N/?)
```

판독: `idevicesyslog | grep -F "[HeartbeatNSE]"`

**확인할 것**
1. `unlocked` 값이 실제로 나오는가(`?`만 나오면 확장에서 키체인 프로브가 안 되는 것)
2. 폰을 쓰고 있을 때 `Y`, 방치했을 때 `N`으로 갈리는가
3. `lag`이 사용 여부와 상관 있는가 (실측 +2분54초 ~ +14분50초)
4. `steps=0`인 날이 얼마나 자주 나오는가

### 18.8 도착 지연은 **이미 쌓인 데이터에서도** 뽑을 수 있다

배포 없이 지금 계산 가능하다.

```
heartbeat_logs.scheduled_key  →  "2026-08-31_19:00" 에서 예약시각
heartbeat_logs.server_ts      →  실제 도착 시각
지연 = server_ts − 예약시각
```

안드로이드까지 같은 방식으로 비교되므로, 임계값 N을 정할 때 근거가 된다.
**n=3(+9분32초 / +14분50초 / +2분54초)으로는 임계값을 정할 수 없다.**

### 18.9 결정하지 않은 것

- 판정에 넣을지 여부, 넣는다면 어떤 조합인지
- ③이 확장에서 실제로 되는지
- ④의 임계값 N
- 안드로이드를 `isKeyguardLocked()`로 바꿀지

⚠️ **"iOS 0보가 얼마나 자주 나오는지 보고 정하자"는 접근은 이 문제를 풀지 못한다.**
빈도가 아니라 **신호의 질**이 쟁점이다 — 지금 안드로이드가 쓰는 신호부터 하루를 대표하지
못한다.

### 18.10 ★ 잠금 상태 프로브 실측 — 4/4 예상대로 (2026-08-31 22:58~23:07)

`probe/ios-lock-signal` 빌드(1.3.2+57 + 계측)를 실기기에 설치하고, admin 엔드포인트로
트리거를 연속 발사하며 폰 상태만 바꿔 관측했다. **하루 한 번 제약이 없다** — 계측이
`already-sent` 분기보다 **앞**에 있어 오늘 안부가 이미 나갔어도 매번 값을 읽는다.

```
22:58:24  nse already-sent unlocked=N lag=238m type=trigger   ← ① 화면 꺼짐 + 잠금
23:03:24  nse already-sent unlocked=N lag=243m type=trigger   ← ② 화면 켜짐 + 잠금
23:05:49  nse already-sent unlocked=Y lag=245m type=trigger   ← ③ 잠금 해제
23:07:02  nse already-sent unlocked=N lag=247m type=trigger   ← ④ 해제 후 화면 끔
```

| # | 폰 상태 | 결과 | 의미 |
|---|---|---|---|
| ① | 화면 꺼짐 + 잠금 | `N` | 기준선 |
| ② | **화면 켜짐 + 잠금** | **`N`** | ★ **화면 켜짐에 속지 않는다** |
| ③ | 잠금 해제 | `Y` | 사람이 조작한 순간을 잡는다 |
| ④ | 해제 후 화면 끔(즉시) | `N` | **유예가 없다** — 창이 매우 좁다 |
| ⑤ | **앱 백그라운드 + 다른 앱 사용 중** | **`Y`** | ★ 잠금 판정이 **앱 상태와 무관**하다. 신호가 재는 것은 "우리 앱을 쓰는가"가 아니라 **"폰을 쓰는가"**다 |
| ⑥ | 앱 포그라운드 | `Y` | 앱이 떠 있어도 **확장은 정상 실행**된다 — 계측 공백 없음 |

⑤가 실무적으로 가장 중요하다. 사용자가 폰을 쓰는 시간의 대부분은 "우리 앱은 백그라운드,
다른 앱 사용 중"인데 그 상태를 놓치지 않는다.

**확정된 것 세 가지**

1. **확장에서 잠금 상태를 읽을 수 있다.** 앱이 킬된 상태에서, 키체인 프로브만으로,
   추가 권한·entitlement·앱 협조 없이. (`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`
   항목을 확장 자기 access group에 쓰고 읽는다.)
2. **안드로이드의 `isInteractive`보다 정확하다.** ②에서 안드로이드는 `true`가 되어
   **사람이 아무것도 하지 않았는데 구제된다**(알림 하나로 화면이 켜져도 참). 이 신호는
   그 오탐이 없다.
3. **정확하지만 창이 좁다.** 화면을 끄는 즉시 `N`이다. 이 신호가 잡는 것은 **"바로 지금
   폰을 보고 있다"** 하나뿐이고, "30분 전에 썼다"는 잡지 못한다.

⚠️ **그래서 단독 판정에는 쓸 수 없다.** 확장은 예약시각 정각에 실행되는데, 19:00 정각에
폰을 보고 있을 확률은 낮다 → 대부분 `N` → 정상 사용자가 무더기로 `suspicious=true`가 된다.
§18.5·§18.6에 적어둔 대로 **여러 구제 조건 중 하나**로만 의미가 있다.

**측정 방법 메모**: `idevicesyslog`는 USB 필수이고, 우리 로그의 프로세스명은
`HeartbeatNSE(Foundation)`이다. `grep -F "[HeartbeatNSE] nse"`로 뽑는다. 며칠짜리 무인
관측을 위해 App Group에 **최근 12건 롤링**으로도 남기며, 앱을 열면 `AppDelegate`가
전부 출력한다(`#1 … #12`).

⚠️ 테스트 중 **자동 잠금을 5분으로 늘려** 잠금화면이 유지되게 했다. 기본값이면 화면이
자꾸 꺼져 ②번 조건을 만들기 어렵다. 끝나면 되돌릴 것.

### 18.11 ★★ 세 신호 모두 확장에서 동작한다 — 후보 확정 (2026-08-31 23:19)

계측 ①(앱 포그라운드 마커)과 ③(움직임 이력)을 추가한 빌드의 첫 실행.

```
23:19:14  nse sent unlocked=Y fg=Y lag=259m type=trigger steps=8 motion=Y
```

| 신호 | 결과 | 판정 |
|---|---|---|
| `unlocked` | `Y` | ✅ (§18.10에서 6/6 검증 완료) |
| **`fg`** | **`Y`** | ✅ 앱 포그라운드 마커 동작. 방금 앱을 연 것이 반영됐다 |
| **`motion`** | **`Y`** | ★ **`CMMotionActivityManager`가 확장에서 동작한다** |
| `steps` | `8` | ✅ CMPedometer (기존 검증) |
| `lag` | `259m` | ✅ 예약 19:00 대비 23:19 |

**`motion`이 이 관측의 핵심이다.** 확장에서의 `CMMotionActivityManager` 가용성은 애플
문서로 확인되지 않아 §18.3에 "미검증"으로 남겨 두었던 유일한 항목이었다. 이제 **세 후보
신호가 전부 확장에서 실현 가능함이 실측으로 확정**됐다.

⚠️ 움직임 조회는 비동기라 3초 상한을 걸어두었다. 시간 안에 못 오면 `motion=?`이 찍히며,
그래도 전송은 지연되지 않는다(계측이 본 동작을 막지 않는다).

### 18.12 세 신호의 성격 비교 — 서로의 사각을 메운다

| 신호 | 범위 | 재는 것 | 강점 | 약점 |
|---|---|---|---|---|
| `steps` | 하루 누적 | 걸었는가 | 활동의 직접 증거 | 거동 불편·폰 두고 이동 시 0 |
| `unlocked` | **그 순간** | 폰을 보고 있는가 | 사람 조작의 확정 증거. 화면 켜짐에 속지 않음 | **창이 극도로 좁다**(화면 끄면 즉시 N) |
| `fg` | 하루 | 앱을 열었는가 | 넓고 결정적 | 앱을 안 여는 것이 정상 사용 패턴이라 대부분 N |
| `motion` | **하루 소급** | 기기가 움직였는가 | **걸음 0이어도 차량 이동·들어올림을 잡는다** | 폰을 책상에 둔 채 활동하면 N |

**`motion`이 가장 유망하다** — 유일하게 *하루 전체*를 *소급으로* 보면서 *사람의 움직임*을
잰다. 안드로이드의 화면 켜짐 스냅샷보다 근본적으로 나은 신호다.

### 18.13 다음 단계

세 신호가 다 되는 것이 확인됐으므로 이제 필요한 건 **분포**다.

```
· 실사용 조건(예약시각 정각 실행)에서 각 신호가 Y/N으로 어떻게 갈리는가
· 특히 steps=0 인 날, 나머지 셋이 구제하는가
· motion=? 가 얼마나 자주 나오는가 (3초 상한이 충분한가)
```

케이블 없이 며칠 두면 App Group 롤링 로그(최근 12건)에 쌓인다. 나중에 USB 한 번 연결해
앱을 열면 `AppDelegate`가 `#1 … #12`로 전부 출력한다.

⚠️ **판정에 넣는 것은 그 분포를 본 뒤다.** 지금 넣으면 임계값도 조합도 근거 없이 정하게 된다.

### 18.14 ⚠️⚠️ 진단 푸시를 실사용자에게 오발송했다 — §9.5 사고의 재발 (2026-09-01 00:19)

프로브 검증을 위해 admin 트리거를 **10여 회** 쐈는데, 대상이 어느새 **3대**로 늘어
있었다. 실사용자 2대가 밤 23시~00시에 반복 수신했다.

```
04B37964…  예약 00:05  ← 테스트 아이폰
DFDBAFD2…  예약 18:00  ← 실사용자. **08-31 미전송 상태였고 내 22:58 푸시로 안부가 전송됨**
B9352A5D…  예약 18:00  ← 실사용자. last_seen 08-30 이후 변화 없음(토큰 사망 또는 오프라인)
```

**두 번의 판단 실패가 겹쳤다.**

1. **22:55에 "3대"를 보고 위험을 짚어놓고도**, "테스트 기기다"라는 답을 확인 없이
   받아들이고 계속 쐈다. 쿼리가 `platform='ios'`로 거르므로 안드로이드 기기는 애초에
   나올 수 없다는 모순을 그 자리에서 눈치챘으면서도 진행했다.
2. **애초에 지정할 수단이 없었다.** 진단 응답은 `device_id`를 8자로 잘라 보여주는데
   필터는 `d.device_id = $1` 완전 일치라, "이 기기 하나만"을 지정하는 것이 **불가능**했다.

**수정**: 접두어 일치로 바꿔 응답에 보이는 8자를 그대로 쓸 수 있게 했고, 파라미터 설명에
*"생략하면 조건에 맞는 모든 기기에 발송된다. 대상이 1대라고 가정하지 말 것 — 실사용자가
새 버전으로 업데이트하면 조용히 늘어난다"*를 명시했다.

⚠️ **불변 규칙**: 진단 발송은 **항상 `device_id`를 지정한다.** 지정 없이 쏘는 것은
"오늘 대상이 몇 대인지"를 매번 확인했다는 전제에서만 안전한데, 그 전제는 조용히 깨진다.
발송 전 `dry_run=true`로 대상 수를 먼저 보는 것도 습관으로 굳힐 것.

⚠️ 이 사고는 §9.5(2026-08-23, 실사용자 22명에게 오발송)와 **같은 유형**이다. 그때는
쿼리 조건 누락이었고 이번은 대상 증가를 놓친 것이지만, 원인은 하나다 —
**진단 도구가 "지금 누구에게 가는가"를 사용자에게 강제로 확인시키지 않았다.**

### 18.15 ★★ `motion`은 `steps`와 대부분 겹친다 — 결론이 단순해졌다 (2026-09-01)

프로브를 만들어 놓고 나서야 드러난 사실이다. **`motion=Y`가 되는 조건이 걸음수와 거의
같은 사건을 가리킨다.**

```
motion=Y 조건 = walking / running / cycling / automotive

walking·running      →  걸음수도 함께 올라간다  →  steps>0 이 **이미** 구제한다
cycling·automotive   →  걸음수 0인데 이동        →  여기서만 새 정보를 준다
```

즉 `motion`이 추가로 구하는 사람은 **"걷지는 않았는데 차를 타거나 자전거를 탄 경우"**뿐이다.
정작 우리가 걱정하는 대상 — 하루 종일 집에서 거의 움직이지 않은 분 — 에게는 `motion`도 `N`이다.

⚠️ **폰을 흔드는 것으로 대조군을 만들 수 없다.** 흔들면 걸음수가 올라가므로 `steps=0`이라는
전제 자체가 깨진다. 그리고 폰을 집어 드는 동작은 이동 분류기에 잡히지 않는다.

**반면 잠금 해제는 `steps`와 완전히 독립이다.** 침대에 앉아 폰만 보는 사람은 걸음수가 0인데
잠금은 푼다 — **거짓 경고를 보내면 안 되는 바로 그 사람**이다.

### 18.16 결론 — 채택 후보와 근거

```
suspicious = false  ←  steps > 0              (움직였다)
                    또는 잠금 해제됨            (폰을 조작했다)   ← §18.10 6/6 검증
                    또는 오늘 앱을 열었다        (하루 단위)      ← §18.11 검증
suspicious = true   ←  그 외
```

| 신호 | steps와 독립? | 검증 | 판단 |
|---|---|---|---|
| `unlocked` | ✅ 완전 독립 | 6/6 통과 | **채택 1순위** |
| `fg` | ✅ 독립 | 동작 확인 | 채택 |
| `motion` | ❌ 대부분 중복 | 동작 확인 | **선택 사항** — 차량·자전거만 |
| `lag`(도착 지연) | 간접 | 미검증 | 보류 — 전파 상태에 좌우됨 |

⚠️ **여전히 넣지 않는다.** 이유는 두 가지다.
1. **분포가 없다.** 테스트폰 1대 데이터뿐이라 "실사용에서 `unlocked=Y`가 얼마나 나오는가"를
   모른다. 확장은 예약시각 정각에 도는데 그 순간 폰을 보고 있을 확률은 낮다(§18.6).
2. **없던 경고 종류를 새로 만드는 변경**이라 보호자 경험이 바뀐다. 별도 릴리스로 다뤄야 한다.

### 18.17 ⚠️ 두 가지 오판 정정 (2026-09-01)

**① "테스트폰에서 며칠 분포를 모으자"는 성립하지 않는다.** 책상에 놓인 테스트폰은 실제
대상자의 생활을 대표하지 않는다. 잠금을 일부러 풀었다 안 풀었다 하는 것은 **우리가 답을
고르는 것**이라 아무것도 알려주지 않는다.

**② "안드로이드 이력으로 iOS를 예측하자"도 틀렸다.** 발화 시점이 구조적으로 다르다(§18.6).

```
안드로이드  워커가 Doze에 막혀 있다가 **사용자가 폰을 켤 때** 풀려 발화
            → 발화 순간 화면 켜짐일 확률이 높다 → suspicious=false 가 잘 나온다
iOS        확장은 **예약시각 정각**에 실행
            → 그 순간 잠겨 있을 확률이 높다 → suspicious=true 가 많아진다
```

**두 플랫폼의 `suspicious=true` 비율은 비교 대상이 아니다.**

### 18.18 그래서 남은 것은 측정이 아니라 결정이다

프로브 검증은 **끝났다**(§18.10 6/6, §18.11). 남은 질문은 "판정을 켤 것인가"이고, 이건
데이터로 미리 답할 수 없다 — 실사용 분포는 **실제로 켜 보거나, 계측을 서버로 보내야** 나온다.

| 선택 | 내용 | 대가 |
|---|---|---|
| **A. 켠다** | `steps>0 OR unlocked OR fg`. 안드로이드와 동작이 같아진다 | 경고가 많아지면 조건 한 줄로 되돌린다 |
| **B. 계측을 서버로** | heartbeat 페이로드에 diag + 서버 컬럼 → 며칠 뒤 근거를 갖고 결정 | 서버 변경 + 대기 |

⚠️ **A의 근거**: 안드로이드는 이미 이렇게 동작한다. iOS만 이 경고를 못 낸 것은 기술적
한계 때문이었고 그 한계가 풀렸다. **두 플랫폼을 같게 만드는 것 자체가 정당한 근거**다.
다만 iOS는 발화 시점 때문에 경고가 더 많이 나올 수 있다는 것을 알고 켜야 한다.

### 18.19 참고 — 왜 프로덕션 배포로는 데이터가 안 모이나

계측값은 **기기 안에만** 남는다(NSLog + App Group). 실사용자 폰은 USB로 꽂을 수 없으므로
**프로브를 프로덕션에 배포해도 데이터가 0이다.** 의미 있게 하려면:

```
heartbeat 페이로드에 diag 필드 추가  +  서버에 컬럼 하나
→ 며칠이면 전 사용자 분포가 쌓인다 → 그때 조합과 임계값을 근거 있게 정한다
```

그때까지 프로브는 `probe/ios-lock-signal` 브랜치에 보존한다. **main 배포에는 넣지 않는다** —
데이터를 못 얻으면서 리스크만 늘린다.

## 19. ★ suspicious 판정 도입 (2026-09-01)

확장이 `"suspicious": false`를 하드코딩하던 것을 실제 판정으로 바꿨다.

```swift
"suspicious": !((steps ?? 0) > 0 || unlockedNow == true || fgToday)
```

### 19.1 왜 지금인가 — 마지막 반대 근거가 무너졌다

도입을 미루던 유일한 이유는 **"iOS는 예약시각 정각에 확장이 돌아 잠금 상태일 확률이 높고,
그래서 안드로이드보다 경고가 많이 나올 것"**이라는 추론이었다(§18.6). **이 추론이 틀렸다.**

```
확장은 정각에 돌지 않는다
  → 푸시는 APNs에 보관됐다가 **기기가 깨어날 때** 배달된다
  → 실측 도착 지연 +2분54초 / +9분32초 / +14분50초
  → 기기를 깨우는 것은 대개 **사용자가 폰을 집어 드는 행위**다 (§10.3)
```

**안드로이드의 "Doze가 풀릴 때 워커가 발화"와 같은 메커니즘이다.** 발화 시점이 사용자
활동과 상관되는 것은 양쪽이 같고, 그렇다면 `unlocked=Y`가 나올 확률도 특별히 낮을 이유가 없다.

### 19.2 안드로이드와 같은 질문을 한다

```
안드로이드  워커 발화 시점에 화면이 켜져 있었는가   (PowerManager.isInteractive)
iOS        확장 실행 시점에 잠금이 풀려 있었는가    (키체인 프로브)
```

둘 다 **"전송 순간에 사람의 조작 흔적이 있는가"**를 묻는다. 오히려 iOS 쪽이 정확하다 —
알림만으로 화면이 켜져도 참이 되는 안드로이드와 달리 잠금 해제는 Face ID나 암호를
요구한다(§18.10 ② 실측).

### 19.3 불변 규칙

1. **구제 조건으로만 쓴다.** 세 신호(`steps>0` / `unlocked` / `fg`) 중 하나라도 참이면
   `false`. `true`는 **셋 다 아닐 때**만 나온다. "잠김"은 30분 전을 모르므로 단독으로
   `true`의 근거가 될 수 없다.
2. **`motion`은 넣지 않는다.** 비동기라 전송 시점에 값이 없을 수 있고, walking·running이
   걸음수를 함께 올려 `steps>0`과 대부분 겹친다(§18.15). 계측으로만 남긴다.
3. **되돌리기는 한 줄이다.** `"suspicious": false`로 바꾸면 즉시 복구된다. iOS에 **없던
   경고 종류가 생기는 변경**이므로, 보호자 경고가 과도해지면 그것이 복구 경로다.

### 19.4 지켜볼 것

iOS 대상자에게 **"⚠ 주의 — 오늘 활동 기록이 없습니다"가 처음으로 발생**한다. 며칠간
보호자 알림 빈도를 보고, 과도하면 §19.3-3으로 되돌린다. 판단 기준은 빈도 자체가 아니라
**"그 경고가 실제로 확인할 만한 상황이었는가"**다.
